# Arrow Puzzle: технический путеводитель

[English](../en/PROJECT_GUIDE.md) | **Русский**

Документ синхронизирован с версией 0.5.0 на 30 октября 2026 года. Он
предназначен для быстрого погружения в устройство и разработку проекта. За
пользовательским описанием игры следует обращаться к корневым `README.md` и
`README_RU.md`.

В исходном репозитории инструкции для агентов находятся в `AGENTS.md`, а
краткая англоязычная дорожная карта и память проекта — в `ai-docs/README.md`.

## 1. Что это за проект

Arrow Puzzle — минималистичная головоломка, в которой поле полностью заполнено
ломаными стрелками. Стрелка движется вперёд подобно змейке: голова занимает
следующую клетку, а хвост освобождает последнюю. Цель — вывести все стрелки за
пределы поля, не потеряв три жизни.

Текущий стек:

- C++20;
- raylib 5.5;
- CMake + Ninja;
- MSVC и статический CRT на Windows;
- статически собранная raylib;
- только стандартная библиотека C++ вне raylib;
- встроенный в EXE шрифт Inter.
- встроенные переводы на восемь языков и поднабор китайского шрифта.

Windows x64 остаётся основной платформой. Нативная Linux x86-64 тоже собирается
и тестируется; зависимости и границы проверки описаны в [LINUX.md](LINUX.md).
Android и native Wayland остаются будущими целями.

Текущему рендеру Windows нужны контекст OpenGL 3.3 Core, GLSL 330 и драйвер,
который их предоставляет. Дискретная видеокарта не обязательна: встроенная
графика с такой поддержкой может использовать тот же рендер. Фактическая
частота кадров на встроенной графике пока не измерялась. Генерация большого
поля выполняется на CPU и не зависит от графического API.

## 2. Продуктовые принципы и обязательные правила

При изменениях важно сохранять следующие решения пользователя:

1. Игра бесплатная, без рекламы, аккаунтов, телеметрии и сетевой активности.
2. Нужны маленький автономный EXE, быстрый запуск, минимум зависимостей и
   практически нулевая нагрузка в простое.
3. Игровое поле имеет тёмную тему по умолчанию и сохраняемую светлую тему.
   Полёт выделяется синим, ошибка — красным. Меню и финальные экраны тёмные.
4. Уровень должен быть плотным клубком из коротких, средних и длинных стрелок,
   а не набором простых S-образных территорий.
5. Генератор не имеет права подменять неудачу скучной построчной змейкой.
   Более долгое ожидание или явная ошибка лучше неинтересного уровня.
6. Уровень обязан быть конструктивно решаемым. Генерация и её качество должны
   оставаться покрыты тестами.
7. Динамический самопроход разрешён только тогда, когда голова приходит в
   собственную клетку ровно в тот тик, когда хвост её освобождает. Настоящее
   столкновение с собой запрещено.
8. Можно запускать несколько стрелок одновременно. Контакт двух движущихся
   стрелок отнимает одну жизнь за эпизод, окрашивает обе в красный, ставит
   полёт на паузу 0,5 секунды, но не возвращает стрелки назад.
9. Столкновение со статической стрелкой или настоящее самостолкновение
   возвращает запущенную стрелку по истории движения. После возврата она
   остаётся красной.
10. Нажатие мыши только «вооружает» стрелку. Запуск при отпускании над той же
    стрелкой возможен, если указатель не сместился больше чем на 6 экранных
    пикселей. Превышение порога перетаскивает поле и отменяет запуск до конца
    жеста, даже при возврате указателя назад. Сохранять клавиатурные масштаб
    и вписывание поля в окно.
11. Сохранение содержит полную геометрию и состояние партии, а не seed. Это
    защищает сохранения от изменений генератора и различий стандартных ГСЧ на
    разных платформах.

Цели CMake:

- `arrow_core` — `Board`, генератор, кинематика, коллизии и persistence без
  зависимости от raylib;
- `arrow_puzzle` — GUI-приложение, связывающее `arrow_core` и raylib;
- `arrow_puzzle_portable` — тот же GUI с данными рядом с исполняемым файлом;
- `arrow_tests` — генератор, качество уровней, кинематика и коллизии;
- `arrow_persistence_tests` — настройки и сохранения;
- `arrow_localization_tests` — переводы, переключение языков и определение локали;
- `arrow_hint_tests` — таймер, случайный безопасный ход, проход хвоста и самостолкновения;
- `arrow_menu_selection_tests` — логика выбора меню без окна;
- `arrow_board_pointer_tests` — клики, перетаскивание и отмена запуска без окна;
- `arrow_end_screen_tests` — состояния и время финальных экранов без окна.

GPU-проверки `arrow_render_tests`, `arrow_ui_text_tests` и проверка звука
`arrow_audio_tests` собираются явно и не входят в обычный `ctest`.

Желательное направление зависимостей:

```text
Types
  ├─ Board ─ Generator
  ├─ MotionKinematics
  ├─ MotionResolver
  └─ Persistence
          \       /
             Game + raylib
```

Ядро должно оставаться пригодным для тестирования без окна и GPU.

## 4. Основные модели данных

### Cell и Arrow

`Cell` — целочисленная координата клетки. `Arrow::cells` всегда хранится от
головы к хвосту. `Arrow::direction` — кардинальный вектор движения. Для стрелки
длиной больше одной клетки обязано выполняться:

```text
cells[0] - cells[1] == direction
```

Соседние клетки тела отличаются ровно на один шаг по горизонтали или
вертикали. В одной стрелке нет повторяющихся клеток.

### Board

`Board` хранит исходную неизменяемую геометрию. Живое состояние игры не
записывается обратно в него — оно находится в `RuntimeArrow` внутри `Game.cpp`.

Ключевые проверки:

- `hasValidGeometry()` проверяет направление, связность и отсутствие повторов;
- `isCompletelyFilled()` требует, чтобы каждая клетка поля принадлежала ровно
  одной стрелке;
- `canExit()` симулирует выход одной стрелки с учётом динамического хвоста;
- `solveGreedily()` служит общей проверкой существования полного порядка
  удаления, но генератор также хранит свой конструктивный порядок неявно.

Подробнее о генерации см. [GENERATOR.md](GENERATOR.md), о состоянии игры —
[RUNTIME.md](RUNTIME.md).

## 5. Сборка на Windows

Нужны Visual Studio 2022 с MSVC x64 и Windows SDK, CMake 3.24+, Ninja и Git.
raylib скачивается через `FetchContent` при первой конфигурации.

Иконки встроены в EXE, включая ресурс Windows для Проводника и ярлыков.
PNG/ICO рядом с игрой не нужны. Обычная сборка использует готовые изображения
из репозитория; обновление изображений описано в
[assets/icons/README.md](../../assets/icons/README.md).

Из обычного PowerShell в корне проекта:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass `
    -File .\tools\build-windows.ps1 `
    -Configuration Release
```

Скрипт конфигурирует, собирает и запускает полный набор тестов. Результат:

```text
build\windows-msvc\arrow_puzzle.exe
```

Debug-сборка:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass `
    -File .\tools\build-windows.ps1 `
    -Configuration Debug
```

Из Developer PowerShell можно использовать presets напрямую:

```powershell
cmake --preset windows-msvc
cmake --build --preset windows-msvc
ctest --preset windows-msvc
```

Если игра блокирует перезапись EXE, определите процесс, запущенный именно из
этого пути. AGENTS.md разрешает завершить его и пересобрать на прежнем месте.

Команды и presets для нативной сборки Linux описаны в [LINUX.md](LINUX.md).

## 6. Тестирование

Полный `ctest` запускает шесть наборов тестов:

```powershell
ctest --test-dir build\windows-msvc --output-on-failure
```

Генераторный тест по умолчанию проверяет более 1 300 полей и набор специальных
сценариев движения. Он намеренно тяжёлый и может выполняться десятки секунд.

Для быстрого воспроизводимого диапазона:

```powershell
.\build\windows-msvc\arrow_tests.exe 25 700
```

Аргументы — количество обычных seed и первый seed. Специальные регрессии всё
равно выполняются. Persistence-тест можно запускать отдельно:

```powershell
.\build\windows-msvc\arrow_persistence_tests.exe
```

Минимальная проверка после изменения:

| Изменение | Обязательная проверка |
| --- | --- |
| Генератор, метрики или длины | Полный `arrow_tests`; несколько визуальных seed |
| Кинематика или коллизии | Специальные motion-регрессии в `arrow_tests` |
| Формат настроек/сохранений | `arrow_persistence_tests`; версия формата |
| UI, ввод или камера | Сборка + автоматический screenshot + ручной запуск |
| CMake, font embedding, релиз | Чистая Release-сборка и запуск EXE вне build tree |

## 7. Автоматизированные визуальные проверки

UI-проверки через переменные окружения компилируются только в Debug. Release
и RelWithDebInfo исключают этот код и строки переменных. Во всех конфигурациях
отключены F12/Control+F12 из raylib. Упаковка требует Release, поэтому хуки
разработки не попадают в релизный пакет:

```powershell
cmake --preset windows-msvc-debug
cmake --build --preset windows-msvc-debug --parallel 2
$env:ARROWPUZZLE_SEED = "747"
$env:ARROWPUZZLE_SCREENSHOT = "$PWD\preview.png"
$env:ARROWPUZZLE_DIFFICULTY = "2"
$qa = New-Item -ItemType Directory -Path (Join-Path $PWD 'out/qa-example') -Force
Copy-Item .\build\windows-msvc-debug\arrow_puzzle_portable.exe (Join-Path $qa 'Game.exe')
& (Join-Path $qa 'Game.exe')
```

Для Windows QA используйте отдельную копию portable Debug-бинарника, как выше,
чтобы не менять личный LocalAppData. В обычной Linux Debug-сборке задавайте
изолированные абсолютные XDG-пути. Переименование сохраняет portable-режим.

Доступные hooks:

- `ARROWPUZZLE_SEED` — воспроизводимый seed;
- `ARROWPUZZLE_DIFFICULTY` — сложность 1..4;
- `ARROWPUZZLE_SCREENSHOT` — путь итогового PNG и автоматическое завершение;
- `ARROWPUZZLE_SCREENSHOT_FRAME` — номер кадра для снимка;
- `ARROWPUZZLE_SCREENSHOT_MENU` — Main/New game/Settings как 1..3;
- `ARROWPUZZLE_SCREENSHOT_REMOVE` — скрыть первые N стрелок;
- `ARROWPUZZLE_SCREENSHOT_LAUNCH` — запустить стрелку по индексу;
- `ARROWPUZZLE_SCREENSHOT_LAUNCH_2` — запустить вторую стрелку;
- `ARROWPUZZLE_SCREENSHOT_LAUNCH_2_FRAME` — кадр второго запуска;
- `ARROWPUZZLE_RESUME` — открыть сохранение в автоматическом сценарии;
- `ARROWPUZZLE_SAVE_ON_EXIT` — проверить сохранение при завершении.

Снимок нужно не только создать, но и визуально просмотреть.

## 8. Рабочий процесс разработки

Перед изменениями:

1. Прочитать этот файл и тематический документ.
2. Выполнить `git status --short` и не трогать несвязанные изменения
   пользователя.
3. Найти текущие реализации и тесты через `rg`, не полагаться только на README.
4. Для генератора сначала сформулировать сохраняемые инварианты и метрики.
5. Для движения разделять непрерывную отрисовку и дискретную симуляцию клеток.

После изменений:

1. Собрать Release или Debug в зависимости от задачи.
2. Запустить пропорциональный риску набор тестов.
3. При визуальных изменениях создать и просмотреть screenshot.
4. Проверить `git diff --check` и `git status --short`.
5. Правила автоматических коммитов и push для ИИ читать в `AGENTS.md`.
   Порядок выпуска релиза описан в [RELEASING.md](RELEASING.md).

## 9. Текущие ограничения и технический долг

- `Game.cpp` — крупный монолит. Вынос UI, рендера и simulation controller в
  отдельные модули упростит изменения, но рефакторинг должен идти маленькими
  тестируемыми шагами.
- Начиная с 0.4.0 Very Hard использует ограниченное построение от фронтов
  в максимум четырёх потоках. В 0.3.0 были значительные пики времени и памяти;
  текущие ограничения и инструмент замеров описаны в руководстве генератора.
- Генератор требует чётные размеры поля.
- Native Wayland и Android не проверены; Linux пока использует X11/XWayland.
- В корне может находиться пользовательский `TODO.txt`. Это пользовательский
  файл; не удалять и не переписывать его без просьбы.

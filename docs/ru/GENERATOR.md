# Конструктивный генератор уровней

[English](../en/GENERATOR.md) | **Русский**

Реализация находится в `src/Generator.cpp` и `src/FrontierGenerator.cpp`, публичный интерфейс — в
`include/arrow/Generator.hpp`, статистические и регрессионные проверки — в
`tests/GeneratorTests.cpp`.

## 1. Контракт generateBoard()

```cpp
struct GeneratorOptions {
    int columns{20};
    int rows{20};
    int minimumLength{2};
    int maximumLength{30};
    std::uint32_t seed{0};
    int candidateAttempts{8};
    bool allowArrowLoops{true};
};
```

Успешный результат обязан:

- иметь положительные чётные размеры не меньше 3 x 2;
- полностью покрывать поле, по одной стрелке на клетку;
- содержать только связные непересекающиеся тела без повторяющихся клеток;
- соблюдать заданный диапазон длин после безопасного clamp;
- иметь конструктивный порядок удаления всех стрелок;
- корректно учитывать динамические самопроходы;
- быть детерминированным для одинаковых options в рамках той же реализации.

При отсутствии подходящего кандидата выбрасывается `std::runtime_error`.
Упрощённого fallback-уровня намеренно нет.

## 2. Общая схема

Описанное ниже разрезание пути сохранено для Simple, Middle, Hard и специальных
ограничений длины. В разработке к 0.4.0 поля с обеими сторонами от 128 клеток,
минимальной длиной 2 и максимальной не меньше 30 используют построение от
доступных фронтов; см. раздел 11. Для узких нестандартных полей сохранено
разрезание пути. Геометрия сохранённых игр не меняется.

```text
случайное остовное дерево сетки 2x2
                ↓
единый гамильтонов цикл по всем клеткам
                ↓
разрыв цикла на границе поля → направленный путь
                ↓
анализ выходных лучей и допустимых интервалов
                ↓
DP/диапазонная достижимость числа стрелок
                ↓
разрез пути на стрелки с корректными зависимостями
                ↓
измерение качества и проверка порядка решения
                ↓
лучший из N параллельных кандидатов
```

## 3. Построение гамильтонова цикла

`makeLabyrinthCycle()` делит поле на макроклетки 2 x 2. Каждая макроклетка
сначала является отдельным четырёхклеточным циклом. На графе макроклеток
строится случайное остовное дерево алгоритмом Краскала с `DisjointSet`.

Каждое ребро дерева разрезает по одному ребру у двух соседних циклов и
сшивает их крест-накрест. Поскольку макрограф — дерево, результатом становится
один цикл, посещающий каждую клетку ровно один раз.

Отсюда жёсткое ограничение: обе стороны поля должны быть чётными.

## 4. Открытие цикла

`findOpenings()` ищет клетки на границе, из которых один из двух обходов цикла
смотрит наружу. `openCycle()` разрывает цикл и разворачивает его при
необходимости. Получившийся `path` задаёт единый порядок клеток, который затем
разрезается на последовательные интервалы.

Каждый интервал становится стрелкой:

- начало интервала — голова;
- конец — хвост;
- направление определяется первыми двумя клетками;
- порядок интервалов одновременно является предполагаемым порядком решения.

## 5. Лучи, интервалы и зависимости

`analyzeRays()` заранее исследует путь головы каждой потенциальной стрелки.
`buildIntervalFacts()` кэширует допустимость диапазонов с учётом:

- минимальной и максимальной длины;
- выхода головы вдоль направления;
- блокирующих клеток других будущих стрелок;
- настоящих самостолкновений;
- разрешённых динамических самопроходов;
- настройки `allowArrowLoops`.

Разрез считается допустимым только тогда, когда зависимости от более ранних
стрелок не нарушают конструктивный порядок удаления.

На небольших полях используется битовая DP достижимости числа стрелок
`reachableArrowCounts()`. На больших полях применяется точная диапазонная
версия `reachableArrowCountsByRanges()`, чтобы избежать плотной таблицы
«площадь × число стрелок». Восстановление конкретного разреза выполняет
`findIntervalsForCount()`; обратный граф зависимостей позволяет обновлять
доступность только затронутых вариантов.

## 6. Длины и число стрелок

`makeLengthProfile()` и `preferredArrowCounts()` формируют широкий набор
коротких, средних, длинных и очень длинных стрелок. Генератор не просто
максимизирует число сегментов: это привело бы к множеству тривиальных стрелок.

Целевое количество начальных ходов зависит от размера, но выбирается случайно
для каждого seed:

| Максимальная сторона | Диапазон стартовых ходов |
| --- | --- |
| до 20 | 2..4 |
| до 40 | 2..5 |
| до 80 | 3..7 |
| больше 80 | вычисляемый диапазон; для 160 x 160 это 6..10 |

Для больших полей границы вычисляются через `clamp(maxDimension / 40 + 2,
4, 8)` и `clamp(maxDimension / 16, 6, 12)`. Это целевой диапазон для поиска,
а не отдельная постпроверка результата, поэтому фактическое число может
незначительно отличаться. Подход создаёт несколько независимых фронтов
распутывания и не выдаёт игроку фиксированную подсказку.

## 7. Метрики качества

`measureTangle()` строит карту владельцев клеток и вычисляет, среди прочего:

- число коротких, средних, длинных и очень длинных стрелок;
- количество поворотов;
- разнообразие четырёх направлений;
- границы между разными стрелками по горизонтали и вертикали;
- повторные появления одной стрелки на scanline;
- заполненность bounding box длинных стрелок;
- количество стартовых и последующих вариантов хода;
- число и сложность точных динамических самопроходов;
- большие прямоугольные S-образные «территории»;
- валидность предполагаемого порядка решения.

`scoreCandidate()` награждает плотное переплетение, баланс направлений,
разнообразие длин и сложные самопроходы с минимальным зазором. Особенно ценны
длинные стрелки, голова которых проходит по клетке хвоста ровно после её
освобождения.

Большие прямоугольные S-образные формы получают очень сильный штраф, поскольку
визуально выглядят как отдельная территория, а не нить в клубке.

Для стандартного 20 x 20 дополнительно действует строгий quality floor
`meetsDefaultQualityFloor()`. Для построения от фронтов действуют дополнительные
жёсткие ограничения раздела 11. Остальные размеры выбирают лучший валидный
кандидат по score и проверяются отдельными тестовыми порогами.

## 8. Параллельные кандидаты и детерминизм

Каждая попытка получает собственный `std::seed_seq`, включающий seed, размеры,
лимиты длины и номер попытки. Попытки запускаются через
`std::async(std::launch::async, ...)`, затем результаты считываются в порядке
номеров и сравниваются детерминированно.

Все четыре preset сейчас используют восемь кандидатов:

| Режим | Поле | max length | candidates |
| --- | ---: | ---: | ---: |
| Simple | 20 x 20 | 30 | 8 |
| Middle | 40 x 40 | 60 | 8 |
| Hard | 80 x 80 | 120 | 8 |
| Very Hard | 160 x 160 | 960 (профиль фронтов ограничивает тела 120 клетками) | 8 |

В `Game.cpp` Hard дополнительно может повторить весь `generateBoard()` до трёх
раз с другим seed, если попытка завершилась `runtime_error`. Другие preset
сейчас получают одну seed-попытку.

Кандидаты нового алгоритма используют не больше четырёх рабочих потоков. На
каждого кандидата отводится до 32 циклов; поиск останавливается на первом
полностью заполненном поле, прошедшем все требования качества. У попыток
независимые RNG, результаты сравниваются по номеру попытки: порядок исполнения
не влияет на выбор поля. Исчерпание попыток — явная ошибка, без ослабления
качества. Меньшие preset сохраняют прежние восемь параллельных попыток.

В 0.3.0 разрезание пути на Very Hard могло ждать самый медленный вариант десятки
секунд, выделяя сотни МиБ под плотные таблицы оценок интервалов. Не возвращать
этот поиск в качестве fallback и не увеличивать параллелизм без замеров.

## 9. Решаемость и роль Board::canExit()

Конструктивный порядок формируется при разрезании path и повторно проверяется
метриками. `Board::canExit()` — независимая динамическая симуляция одной
стрелки: она исключает клетку хвоста из self-collision на текущем тике, потому
что хвост освобождает её одновременно с движением головы.

`Board::solveGreedily()` многократно удаляет все доступные стрелки и должен
вернуть полный список. Тесты проверяют не только это, но и геометрию, полное
покрытие, распределение длин и статистическое качество по множеству seed.

## 10. Как безопасно менять генератор

Перед правкой зафиксировать, какой именно показатель нужно улучшить. После
правки обязательно:

1. Проверить несколько фиксированных seed до и после изменения.
2. Запустить полный `arrow_tests`.
3. Сравнить диапазоны числа стрелок, стартовых ходов и length mix.
4. Визуально проверить минимум 20 x 20, 40 x 40 и затронутый крупный preset.
5. Измерить время как минимум на нескольких seed, а не на одном.
6. Убедиться, что `allowArrowLoops=false` остаётся работоспособным.
7. Не ослаблять пороги тестов только ради прохождения новой реализации без
   явного продуктового обоснования.

Особенно опасные изменения:

- смена ориентации `path` или трактовки «head first»;
- статическая проверка self-collision вместо пошаговой;
- сохранение только seed вместо геометрии;
- случайность из общего shared RNG в параллельных задачах;
- fallback на простой serpentine board;
- полный перебор площади × числа стрелок на 160 x 160 и крупнее.

## 11. Построение большого поля от фронтов (разработка к 0.4.0)

Случайное макродерево по-прежнему задаёт извилистый гамильтонов цикл. Однако
генератору больше не нужно следовать одному общему направлению или решать
огромную DP по числу стрелок. `partitionFromFrontiers()` удаляет доступный
непрерывный фрагмент в любом из двух направлений, записывает стрелку и
обновляет затронутые фронты. Когда поле опустело, порядок этих действий уже
является решением. Только полное разбиение может стать кандидатом.

У каждой клетки две возможные головы. Компактные массивы хранят доступную
длину тела, границу самостолкновения и текущую необходимую длину. Если выходной
луч встречает позицию тела `k` на такте `d`, самопроход допустим при
`length <= k + d`; при запрещённых петлях необходимо `length <= k`. Все ещё
занятые клетки луча обязаны принадлежать выбранному телу, остальные должны
быть удалены ранее. Это динамическая проверка освобождения хвоста, а не
статический запрет пересечения с исходным положением тела.

Разрез не может оставлять одиночную клетку ни с одной стороны. Сохраняются
чётные и нечётные длины. Кэш непрерывной длины использует маркер
`lengthLimit + 2`, чтобы отличать остаток из одной клетки от более длинного.
После разреза пересчитываются только головы на затронутых строках, столбцах и
ближайших фрагментах цикла. Индексированные множества хранят каждую доступную
голову один раз, без растущей очереди устаревших записей и обратного графа
лучей. Построение от фронтов требует O(площадь поля) рабочей памяти; прежняя
итоговая оценка качества отдельно строит граф зависимостей.

На один выбор берутся 48 фронтов и небольшой диапазон длин. Смесь коротких,
средних и длинных стрелок, штраф за короткие стрелки на краю и предпочтение
тел, связывающих край с внутренней областью, устраняют однообразную кайму.
Стартовые стрелки предпочтительно длиннее: они освобождают полезные внутренние
пути. Длинные тела, почти полностью заполняющие прямоугольник, отвергаются.
Профиль ограничивает длину `min(заданный максимум, 120)`; максимум из options
остаётся верхней границей, а не обещанной длиной.

Полный кандидат обязан иметь четыре направления, корректный порядок решения,
отсутствие длинных прямоугольных территорий, 30..60% коротких стрелок, минимум
30% средних и 9% длинных. Коротким стрелкам (до 5 клеток) может принадлежать
не больше 20% клеток периметра; минимум 75% периметра должны принадлежать
стрелкам, заходящим внутрь поля. Число начальных ходов должно входить в диапазон
раздела 6: для Very Hard это 6..10. При выключенных петлях требования те же.

### Воспроизводимые замеры

Собрать отдельную цель `arrow_generator_benchmark` в Release, затем выполнить:

```powershell
.\tools\benchmark-generator.ps1
.\tools\benchmark-generator.ps1 -NoLoops -OutputCsv build\generator-no-loops.csv
```

Каждый seed запускается в новом процессе. CSV содержит время генерации,
пиковый рабочий набор Windows в МиБ, количество стрелок, метрики периметра,
хеш геометрии и результат независимой проверки решения. Эта проверка не
включена во время генерации, память замеряется до неё. `-1` означает отсутствие
метрики памяти. Это процесс игрового ядра, без рендера и GPU-ресурсов игры.
Параметр `-Executable` позволяет сравнить другую сборку на том же компьютере.
Регрессии охватывают несколько seed Very Hard в обоих режимах петель,
прямоугольные поля, лимит длины, нечётные длины и повторяемость при параллельном
исполнении.
